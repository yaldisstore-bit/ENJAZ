# ENJAZ Roadmap Provenance

This document exists to prevent future confusion between historically verified roadmap items and later canonicalized delivery sequencing.

## Historically verified / already agreed

The following are independently supported by the project history, repository state, stored specifications, and prior agreed plan:

- Phase 0 — Product/specification freeze and migration contracts.
- Phase 1.1 — Project Foundation.
- Phase 1.2 — Database Architecture.
- Phase 1.3 — Auth & Security.
- Phase 1.4 — Data Layer.
- Phase 1.5 — Foundation Destruction.
- Phase 2.1 — Visual Identity Foundation.
- Phase 2.2 — Design Tokens.
- Phase 2.3 — Typography & RTL System.
- Phase 2.4 — Core Component System.
- Phase 2.5 — Motion & Interaction System.
- Phase 2.6 — Mobile & Android Hardening.
- Phase 2.7 — Premium Pattern Library.
- Phase 2.8 — Visual Destruction & Quality Gate.
- Phase 2 exits with ENJAZ Design System 1.0 before real screen construction.
- Phase 3 begins with App Shell / Top Bar / Bottom Navigation / navigation and actual product structure.
- No legacy UI DNA from R4/R6/V7/V8 is permitted.
- No phase transition before a real quality/release gate.

## Recovery limitation discovered on 2026-09-03

The original roadmap had not previously been committed as one complete standalone file. Archived project files preserve Phase 0 contracts and individual implemented Phase 2 documents, but the exact historical numbering/naming of every stage after the start of Phase 3 could not be recovered verbatim from stored artifacts.

Therefore the project must never pretend that an unrecoverable historical label is a verbatim quote from the old conversation.

## Canonicalization rule

`docs/ENJAZ_MASTER_ROADMAP.md` now freezes the complete delivery path through `ENJAZ 1.0 — Delivered`.

- The verified historical sequence is preserved.
- The post-Phase-3 delivery sequence is derived from the frozen Phase 0 feature inventory, domain contracts, legacy import contract, non-negotiable rules, and known approved ENJAZ capabilities.
- From the merge of this roadmap onward, that complete document is the official roadmap source of truth.
- If an older authoritative artifact is later recovered and proves that a historical stage label differed, the discrepancy must be documented explicitly in a roadmap change; implementation must not be silently reordered.

This provenance record is deliberately permanent so future sessions cannot repeat the mistake of assuming that an absent memory excerpt means a phase never existed.
